# 006 Dialog-based plot configuration

Source inspiration (concept only, nothing copied):
- https://en.wikipedia.org/wiki/Dialog_box (general, vendor-neutral description of the modal-dialog pattern: a window with labelled input fields and commit/cancel buttons; public, 2026-10-28). Concept taken only: a form-style dialog is the standard way countless kinds of software (not just engineering-calculation tools) collect several related settings at once. The dialog *shape* used below (title bar, OK/Cancel/Apply buttons, labelled input rows) is plain OS/toolkit chrome, the same chrome this app's existing Save/Save-As dialogs already use; it needs no further citation.
- No Mathcad, Mathematica, Maple or other vendor software, documentation or screenshot was read or consulted for this spec. No vendor dialog's field order, labels, icons, button wording or exact workflow is described or used anywhere below. Field grouping, list/add/remove design, unit-field placement, error attribution and the Apply behaviour are this spec's own design choices.
- Note for the manager: this spec replaces spec 005 (inline placeholder slots drawn on the chart's axes), which is superseded and not implemented, per Theo's decision of 2026-10-28 recorded in docs/board/decisions.md ("Decided 2026-10-28 (Theo, plot editing UI)"). The reason recorded there is that spec 004's own IP check had deliberately avoided placeholder-on-chart-axis editing as a known patent-sensitive interaction *style* in the engineering-calculation-tool category; a labelled modal dialog is a different, much more generic pattern. See IP check below. This spec reuses one piece of spec 005's design, the "decompose existing text into fields, or fall back to raw text" sub-problem (spec 005's criterion 17 and its Advanced/raw-mode section), because that is a text-decomposition problem, not a placeholder-UI design; no inline-slot/placeholder design from spec 005 is reused.

Interop: this is a GUI-only presentation layer on top of spec 004 (phase A). It does not change `livesheet/engine/plotting.py` (`PlotTrace`, `PlotData`, `nice_axis`, `build_plot`) and does not change `livesheet/document.py` (`RegionData` keeps storing `text` plus optional `w`/`h`; `FORMAT_VERSION` stays as spec 004 left it). A plot configured through the dialog compiles to exactly the same plot-spec text spec 004 already parses, so every acceptance criterion of spec 004 (1-27) keeps holding unchanged; this spec only adds criteria for the new entry point into editing.

Size: two phases, about 3.5-4 days total.
- **Phase D1 (dialog shell, fields, compile/decompose, OK/Cancel)**: the dialog widget, Function(s) list with add/remove, Variable(s) field (existing-name mode and sampling mode), Y/X min-max fields, X/Y unit fields, Title/X label/Y label fields, compiling to spec 004's text format, decomposing existing text into the fields (or detecting "not representable"), OK and Cancel. About 2 days.
- **Phase D2 (Apply/live update, per-field error display, raw-text fallback)**: the Apply button writing into the region and triggering the existing evaluation pass, attributing engine error messages to the field that most likely caused them (or a dialog-wide banner when no single field is responsible), the "Edit as text..." escape hatch and the reciprocal "Use dialog..." control in the raw editor. About 1.5-2 days.

---

## User story
As an engineer placing or editing a plot, I open a small form instead of writing the plot as a block of text: I list the expression(s) I want to see, say which variable they run over (or set up a quick private sweep), optionally pin down the axis ranges and units, and confirm. I still get the exact same chart spec 004 already draws; nothing about how the chart itself looks or is computed changes, only how I fill it in.

## Behaviour (own words)

### Trigger
- `Insert > Plot` and the canvas "Plot here" entry create a plot region at the clicked position (same placement rule as spec 004 phase A2) and immediately open the dialog on it, instead of today's behaviour of starting the region directly in the multi-line text editor with starter text. The region exists on the canvas while the dialog is open (needed for Apply, see below) but shows no chart yet (same "hint, no error" presentation spec 004 already uses for an empty spec).
- Double-clicking an existing plot region opens the dialog pre-filled from its current compiled text, when that text is representable by the fields (see Advanced/raw-text fallback for the exact rule); otherwise double-click opens spec 004 phase A2's existing multi-line text editor directly, unchanged from today.
- The dialog is modal (it blocks input to the rest of the window while open, like the app's existing Save/Save-As dialogs), with a title bar and OK / Cancel / Apply buttons. This is standard dialog chrome, not a bespoke design.

### Fields
- **Function(s)**: a vertical list of single-line text rows, one expression per row, in on-screen order. An "Add function" button beneath the list appends a new empty row (disabled once 20 rows exist, the existing `MAX_TRACES`). Each row has its own "Remove" button that deletes that row and shifts the rows below it up by one (a plain add/remove list, the same generic pattern as any settings dialog with a repeatable list of items; not spec 005's "clear the text to remove" gesture, which was tied to its now-superseded inline-slot design). A row left blank is simply skipped when compiling (no blank `show` line is ever produced), so the user does not have to explicitly remove a row they decided not to fill in. Maps to one `show` line per non-blank row, in on-screen order; the resulting `style_index`/trace order therefore follows row order, same rule spec 004 already uses for `show` lines.
- **Variable(s)**: one field, read as "the x-axis variable, together with its sampling settings" rather than literally "more than one x-variable" (spec 004 allows exactly one `over` per plot; see Open question 1). It has two modes, chosen with a small switch at the top of the field:
  - *Use existing*: one text box for a name already defined above the plot (a range variable or a vector). Maps directly to `over NAME`.
  - *Sample a new range*: four sub-fields, "name", "from", "to", "points" (points optional, same default 101 and same 2-10000 bound as spec 004). Maps to `over NAME from FROM to TO points POINTS` (the `points` word and value omitted when the sub-field is left at the default).
  The dialog does not check whether a typed existing name is actually defined until OK/Apply (same deferred-to-engine rule as Function(s) rows; see Error handling).
- **Y min/max** and **X min/max**: two fields, each two boxes (min, max). A box may contain a plain number, a number with a unit (for example `8 s`, exactly as spec 004's `xlim`/`ylim` values already accept), or be left blank. Blank means automatic for that side. Typing the word `auto` into a box has the same effect as leaving it blank (accepted as a convenience, not required). Both boxes blank omits the `xlim`/`ylim` line entirely (full automatic, spec 004's existing default); one box filled and the other blank compiles to the half-automatic form (`xlim auto to 8 s` or `xlim 8 s to auto`); both filled compiles to the literal `LO to HI` form.
- **X unit** and **Y unit**: one small text box each, placed next to the matching min/max field but editable independently of it (a plot can have a chosen display unit with fully automatic limits). Maps to `xunit`/`yunit`; blank means no line, i.e. spec 004's existing automatic-unit default. This is this spec's own design call (Theo's phrasing named four field kinds; this adds two more, see Open question 2) because without it a user could not choose a display unit unless they also pinned down manual limits, which would be a real gap versus today's text editor.
- **Title**, **X label**, **Y label**: three optional single-line text boxes, grouped together below the axis fields. Maps to `title`/`xlabel`/`ylabel`; blank means no line (spec 004's existing default labelling). Added because the dialog has room for them and it keeps the common case fully representable without dropping to raw text (see Advanced/raw-text fallback; also Open question 3).

### Compiling to the existing text format
The dialog state compiles, always in this fixed order, to exactly the text spec 004 already parses: `plot`, then one `over ...` line from the Variable(s) field, then one `show ...` line per non-blank Function(s) row in on-screen order, then `xunit ...` if set, then `yunit ...` if set, then `xlim ...` if either box is filled, then `ylim ...` if either box is filled, then `title ...` if set, then `xlabel ...` if set, then `ylabel ...` if set. This is what is written into `RegionData.text` (no document-format change) and handed to `Engine.evaluate`/`build_plot` (no engine change). Spec 004's parser does not require a fixed line order beyond the first line being `plot`, so this fixed compile order is only for determinism, not a parser requirement.

### OK / Cancel / Apply
- **Apply** writes the current compiled text into the region's `RegionData.text` and lets the normal `Engine.evaluate` pass run as it already does for every text change; the region's chart (visible on the canvas, to the side of or behind the dialog, depending on where the dialog happens to sit) updates with the fresh `PlotData`, exactly as it would if the same text had been typed into today's multi-line editor. The dialog stays open. This gives a "live update" without any new engine entry point or duplicated plotting call (see note under Open question 4 about the dialog possibly covering the chart).
- **OK** performs the same write as Apply and then closes the dialog.
- **Cancel** on a region that was brand-new when the dialog opened (Apply was never pressed, or was pressed but the region had no previously-saved text) discards the region entirely — the same rule as leaving any other freshly inserted, still-empty region. Cancel on a region that already had a valid, previously-saved plot before the dialog opened reverts `RegionData.text` to that saved text, discarding anything typed or Applied during the dialog session; no partial change from the dialog remains.

### Error handling
- Everything the dialog itself can check without calling the engine is checked first, on OK/Apply, before compiling: Variable(s) must be filled (own message "Variable(s) is required", since a `plot` text without `over` is a case the dialog simply never produces); Function(s) must have at least one non-blank row ("At least one function is required"); a filled min and max on the same axis must have min below max in the given units, when the dialog can compare them directly (own message, reusing spec 004's exact wording "lower limit must be below upper limit" when it is this specific case and otherwise deferring to the engine); a filled `points` sub-field must be an integer, with out-of-range values deferred to the engine's own message.
- Anything else is only known once the compiled text is actually evaluated (OK/Apply calls the normal engine path). If evaluation reports an error, its exact message (spec 004's own wording, nothing invented) is shown:
  - next to a specific Function(s) row, when the message's quoted part matches that row's text (for example an undefined-name or wrong-shape message naming that row's expression);
  - next to the Variable(s) field, when the message is about `over` (undefined name, wrong kind, bad range, out-of-range `points`, mismatched units on the sampling range);
  - next to the relevant min/max field, when the message is about `xlim`/`ylim` (mismatched units, lower-not-below-upper);
  - next to the relevant unit field, when the message is about `xunit`/`yunit`;
  - as a dialog-wide banner above the buttons, when the message does not clearly belong to one field (for example "different units" across two Function(s) rows, or any message that does not match any single field's text).
  In every error case the dialog stays open and the region is left as it was before this OK/Apply press (if Apply had previously succeeded once, that prior, valid state remains on the canvas; the failed attempt is not written).

### Advanced/raw-text fallback
A region's current compiled text is "representable" by the dialog exactly when it has one `over` line, one to twenty `show` lines, and at most one each of `xunit`, `yunit`, `xlim`, `ylim`, `title`, `xlabel`, `ylabel`, and nothing else (this extends spec 005's criterion-17 rule, which covered `over`/`show`/`xunit`/`yunit`, by also allowing `xlim`/`ylim`/`title`/`xlabel`/`ylabel` now that those have fields too; see Open question 6). A representable text decomposes directly into the fields described above. A non-representable text (any phase-B-only keyword such as `xscale`/`style`/`against`/`mode`, more than one `over`, or any unrecognised line) cannot be opened in the dialog at all: double-click opens spec 004 phase A2's existing raw multi-line text editor instead, unchanged.
The dialog itself also offers an **"Edit as text..."** button (next to Cancel) that closes the dialog and opens the same raw multi-line editor on the region's current compiled text (or, for a brand-new region, spec 004 phase A2's existing starter text), with that editor's existing commit rules unchanged. Conversely, whenever the raw editor's current text is representable, it offers a **"Use dialog..."** control that closes the raw editor and reopens this dialog, decomposing the text exactly as double-click would; when the current raw text is not representable, that control is unavailable and a short note says why.

### Resize, move, delete, save/reload — unchanged
These behave exactly as today's `PlotRegion` (spec 004 criteria 25-26 and the GUI rules in `gui/regions.py`): `region.set_size`, the resize handle, moving, selecting, and single-owner deletion (the G4 regression) are not redesigned here. Saving and reloading store and restore exactly the same `text`/`w`/`h` as spec 004; which editing surface (dialog or raw editor) a region opens into on the next interaction is re-derived from the stored text (see Advanced/raw-text fallback above), it is not itself a saved property.

## Syntax proposal (own keywords)
No new engine syntax. The compiled text uses only spec 004's existing keywords (`plot`, `over`, `show`, `xunit`, `yunit`, `xlim`, `ylim`, `title`, `xlabel`, `ylabel`) in the fixed order given under "Compiling to the existing text format". No new statement kind, no change to `livesheet/engine/syntax.py`.

## Acceptance criteria
GUI-level; `P` means the plot region's compiled text and `region.result.plot` after OK (or Apply). References to "criterion N of spec 004" mean `docs/board/specs/004-plots.md`'s numbered acceptance criteria and reuse its exact sheets/numbers.

Trigger and pre-fill
1. `Insert > Plot` (or "Plot here") opens the dialog immediately with Function(s) showing one blank row, Variable(s) empty (existing-name mode by default), Y min/max, X min/max, X unit, Y unit, Title, X label, Y label all blank. Clicking Cancel immediately leaves no region on the canvas at all.
2. Double-clicking an existing plot region whose stored text is `plot\nover t\nshow v*t` (spec 004 criterion 1's text) opens the dialog pre-filled: Variable(s) in existing-name mode with `t`; Function(s) one row `v*t`; every other field blank.
3. Double-clicking an existing plot region using `plot\nover x from 0 to 6.283185307179586 points 5\nshow sin(x)` (criterion 4's text) opens the dialog pre-filled: Variable(s) in sampling mode, name `x`, from `0`, to `6.283185307179586`, points `5`; Function(s) one row `sin(x)`.
4. Double-clicking an existing plot region using `plot\nover t\nshow v*t\nxlim 2 s to 8 s\nylim 0 m to 40 m` (criterion 7's limits on criterion 1's sheet) pre-fills X min `2 s`, X max `8 s`, Y min `0 m`, Y max `40 m`, with X/Y unit left blank.
5. Double-clicking an existing plot region whose text contains a phase-B-only line (for example `xscale log`) or any other non-representable content opens spec 004 phase A2's raw multi-line editor directly, unchanged from today's single-editor behaviour.

Fields and compile mapping
6. Filling Variable(s) = `t` (existing mode) and Function(s) row 1 = `v*t`, then clicking OK on the sheet of spec 004 criterion 1, compiles to `plot\nover t\nshow v*t` and gives `region.result.plot` identical to criterion 1 (same x, y, units, labels, limits, ticks).
7. Filling Variable(s) in sampling mode (name `x`, from `0`, to `6.283185307179586`, points `5`) and Function(s) row 1 = `sin(x)`, then clicking OK on an otherwise empty sheet, compiles to `plot\nover x from 0 to 6.283185307179586 points 5\nshow sin(x)` and gives a result identical to criterion 4.
8. Clicking "Add function" on the dialog from criterion 6 adds an empty row; filling it with `2*v*t` and clicking OK compiles to `plot\nover t\nshow v*t\nshow 2*v*t` and gives a result identical to criterion 3 (two traces, second `style_index == 1`).
9. Clicking a row's "Remove" button deletes that row and shifts the rows below it up by one; the compiled `show` order (and so `style_index`) follows the remaining on-screen order.
10. "Add function" is disabled once 20 non-blank rows exist (criterion 13's 21-trace case cannot be produced from the dialog at all).
11. Setting Y min `0 m`, Y max `40 m`, X min `2 s`, X max `8 s` and clicking OK on sheet 1 adds `xlim 2 s to 8 s` and `ylim 0 m to 40 m` to the compiled text and reproduces criterion 7's result.
12. Leaving X min blank and X max `8 s` compiles to `xlim auto to 8 s` and reproduces criterion 8's half-automatic result; leaving both X min and X max blank omits the `xlim` line entirely.
13. Setting X unit to `ms` (X min/max left blank) adds `xunit ms` to the compiled text and reproduces criterion 2's unit conversion on the x axis; clearing it back to blank removes the `xunit` line.
14. Filling Title `Speed` and leaving X label/Y label blank adds `title Speed` and nothing else beyond the existing default `xlabel`/`ylabel` behaviour; leaving Title/X label/Y label all blank omits all three lines.

OK / Cancel / Apply
15. Clicking "Apply" on a freshly inserted, not-yet-saved plot region with valid Function(s)/Variable(s) writes the compiled text into the region and triggers the normal `Engine.evaluate` pass; `region.result.plot` updates to the new data while the dialog stays open. Clicking OK afterwards performs no further change beyond closing the dialog.
16. Clicking Cancel on a brand-new plot region on which Apply was never pressed removes the region entirely; no `plot` text is left in the document.
17. Opening the dialog on an existing, previously-saved valid plot (criterion 2's region), changing fields (including one Apply press), then clicking Cancel, reverts `RegionData.text` to the text that was saved before the dialog was opened; none of the dialog-session changes remain.
18. Clicking OK has the same net effect on the document as pressing Apply once and then closing the dialog.

Errors
19. On the sheet of spec 004 criterion 1, opening the dialog and setting Function(s) row 1 to `Y` (undefined), then clicking OK: the message `Y is not defined` (criterion 14's wording family) is shown next to that row; the dialog stays open and the region is unchanged.
20. Setting Function(s) to two rows `v*t` and `t` (different dimensions) and clicking OK: the message `different units` (criterion 16's wording) is shown as a dialog-wide banner, since it does not identify a single row.
21. Leaving Variable(s) empty and clicking OK: the dialog's own message "Variable(s) is required" appears next to that field without any engine call (the engine's own `over`-missing error, criterion 13, is never actually produced by this dialog).
22. Setting X min `5 m` on sheet 1 (a seconds axis) and clicking OK: the message `Units do not match` (criterion 16's wording) is shown next to the X min/max field.
23. Setting X min `8 s`, X max `2 s` and clicking OK: the message `lower limit must be below upper limit` is shown next to the X min/max field (caught by the dialog's own check, same wording as criterion 16).

Raw-text fallback
24. "Edit as text..." closes the dialog and opens spec 004 phase A2's existing multi-line editor on the region's current compiled text (or the existing starter text for a brand-new region); that editor's existing commit rules (criterion 25) are unchanged.
25. From a raw editor whose current text is representable, "Use dialog..." closes the raw editor and reopens this dialog, pre-filled exactly as criteria 2-4 describe for double-click; when not representable, that control is unavailable.

Edge cases as acceptance criteria
26. Changing Variable(s) from `t` to a vector `X` (spec 004 criterion 5's sheet) while Function(s) rows are filled only re-validates on the next OK/Apply; a row whose expression is now the wrong shape for the new mode shows its own error (criterion 15's "needs a single value"/"needs a vector" wording) at that row instead of silently keeping stale data.
27. A Function(s) row's text wider than the row's on-screen width is shown elided (trailing ellipsis) while not focused and scrolls to keep the caret visible while being edited; it never wraps to a second line.
28. Clicking OK with an empty Function(s) list (no rows, or all rows blank): for a brand-new region this is simply Cancel's discard behaviour (criterion 16) since nothing valid was ever applied; for an existing region being edited, OK is refused with the dialog's own "At least one function is required" message (the engine's `show`-missing error, criterion 13, is never actually produced by this dialog).

Save/reload and regression
29. Save and reload round-trip exactly as spec 004 criterion 21/25 (`text`, `w`, `h` unchanged); which editing surface (dialog or raw) a region opens into next is re-derived from the stored text (criteria 2-5), it is not a saved property.
30. Resize handle (minimum 200x140, grid-snapped), moving, selecting and single-owner deletion behave exactly as spec 004 criteria 25-26; only the entry point into editing (dialog first, instead of the multi-line text editor starting immediately) and its pre-fill differ from today.
31. PDF export of a plot configured via the dialog is identical to configuring the same plot via raw text (spec 004 criterion 27); the dialog itself is never drawn into the export.

## Edge cases
- A `points` sub-field value outside 2-10000, or non-integer, is caught by the dialog's own check with spec 004's exact wording ("points must be between 2 and 10000"), shown at the Variable(s) field, before any engine call.
- The Variable(s) field's "use existing" mode does not check whether the typed name exists until OK/Apply, the same deferred-to-engine rule as Function(s) rows (see Error handling).
- More Function(s) rows than fit the dialog's visible height scroll within the dialog using the host toolkit's ordinary scrolling, not a bespoke control.
- Nothing about focus or keyboard order in this dialog is bespoke: it uses the toolkit's normal Tab order across fields and buttons. This is a deliberate difference from spec 005's custom Tab/Shift+Tab/Arrow-key scheme for its on-canvas slots, which is dropped along with the rest of spec 005's design.
- Descending ranges, single-point ranges/vectors, very large/small magnitudes and reading-order rules all behave exactly as spec 004 already defines; nothing here changes those numbers.
- A Function(s) row calling a user function defined above the plot (`f(t)`) works exactly as it does in today's text spec.

## IP check
Pass. This design replaces spec 005's inline placeholder slots (drawn live on the chart's own axes), which spec 004's own IP check had deliberately avoided as a known patent-sensitive interaction *style* in the engineering-calculation-tool category, and which spec 005 itself flagged for a human/legal check for that reason. The dialog here is materially lower risk: a modal form with labelled text fields, an add/remove list, and OK/Cancel/Apply buttons is one of the most generic UI patterns in all of software (file dialogs, preference panes, chart-configuration forms in spreadsheets, any properties editor), not a technique specific to, or associated with, engineering-calculation tools, and it is not drawn on or interleaved with the chart's own axes at any point — the chart and the dialog are two separate widgets. The one place this design comes closest to "live" behaviour is the Apply button updating the region's chart while the dialog stays open; this is checked explicitly against the flagged technique and found different in kind: Apply is a conventional, widely-used dialog affordance (seen in font dialogs, cell-format dialogs, and countless preference panes that show a live preview pane), it does not involve typing or clicking directly on the chart's drawn axes, and no part of the chart itself becomes an editable field. No vendor dialog's field order, labels, icons, button wording or workflow was read, described or used; field grouping, the list/add/remove design, the unit-field placement, the error-attribution rule and the Apply/Cancel-revert behaviour are this spec's own choices. No known patent concern for a standard labelled-field configuration dialog; not legal advice.

## Fits current architecture?
- `livesheet/engine/plotting.py`, `livesheet/engine/syntax.py`, `livesheet/document.py`: unchanged.
- New `livesheet/gui/plotdialog.py`: the dialog widget (Function(s) list with add/remove rows, Variable(s) field with its two modes, Y/X min-max fields, X/Y unit fields, Title/X label/Y label fields, OK/Cancel/Apply), plus the two helper functions `compile_plot_fields(...) -> str` (fields to spec-004 text, the Compiling section's fixed order) and `decompose_plot_text(text) -> fields | None` (the inverse, returning `None` for non-representable text, extending spec 005's `is_plot_spec`/`engine_source`-style helpers to also cover `xlim`/`ylim`/`title`/`xlabel`/`ylabel`).
- `livesheet/gui/plotregion.py`: on double-click, calls `decompose_plot_text`; opens this dialog when it succeeds, otherwise opens today's existing multi-line editor unchanged. The existing multi-line editor gains the small "Use dialog..." control described above, calling the same `decompose_plot_text` check.
- `livesheet/gui/worksheet.py`, `livesheet/gui/main_window.py`: `Insert > Plot` / "Plot here" create the region (unchanged placement/sizing) and then open this dialog on it instead of starting the multi-line editor directly; Apply/OK write into `RegionData.text` and rely on the existing `Engine.evaluate` re-run already triggered for every text change (no new evaluation path).
- `livesheet/gui/plotview.py`: unchanged; `paint_plot` keeps drawing from `PlotData` only; the dialog is a separate top-level widget, never drawn into the chart or the PDF export.
- Tests: new `tests/test_plot_dialog.py` or `tests/test_gui_plot_dialog.py` for criteria 1-31 (Qt parts skip when PySide6 cannot load, as today); existing `tests/test_plot.py` and `tests/test_plot_gui.py` need no changes since the engine and `paint_plot` are untouched. The tester should also launch the real app and exercise: Insert > Plot opening the dialog, filling/Applying/OK on a fresh plot, double-clicking an existing plot (both representable and not), add/remove function rows, the unit and limit fields, Cancel on both a new and an existing plot, the error banner/field messages, the "Edit as text..."/"Use dialog..." round trip, and save/reload — on Theo's Mac, not only headless.

## Open questions for the manager (copy to docs/board/decisions.md if accepted)
1. Variable(s) is read as one field (matching spec 004's "exactly one `over`"), carrying either an existing name or a private sampling range's settings, rather than literally several x-variables. [Recommend this reading; please confirm it matches what Theo meant by the plural wording.]
2. X unit / Y unit as two dedicated fields, separate from the min/max fields, to reach `xunit`/`yunit` independently of manual limits (Theo's phrasing named four field kinds; this adds two more). [Recommend keeping them — without them a user could not pick a display unit while limits stay automatic, a real gap versus today's text editor — but flagging since it goes beyond the four named fields.]
3. Title / X label / Y label as three extra optional fields, instead of leaving them raw-text-only. [Recommend keeping them, cheap given the dialog's extra room, and it keeps the common case fully representable; confirm.]
4. Apply updates the live region/chart behind or beside the dialog rather than rendering a separate preview inside the dialog itself, so the chart may be partly or fully hidden by the dialog while it's open. [Recommend accepting this for phase D1/D2; an embedded mini-preview inside the dialog is a possible, costlier follow-up if Theo finds this awkward in practice.]
5. The error-attribution rule (matching an engine error message's quoted part to a Function(s) row, or falling back to a dialog-wide banner) is a heuristic, not a guaranteed exact mapping for every message spec 004 can produce. [Recommend accepting it for now; revisit only if testers find mis-attributed messages confusing in practice.]
6. The "representable" rule for opening a region directly in the dialog now also covers `xlim`/`ylim`/`title`/`xlabel`/`ylabel` (extending spec 005's narrower rule, which stopped at `over`/`show`/`xunit`/`yunit`). [Recommend confirming this extended rule; it is a direct, low-risk extension of the same text-decomposition idea spec 005 already worked out, not a new design.]
7. Keep the reciprocal "Use dialog..." control in the raw multi-line editor (a plain mode-switch button, not an inline-placeholder control) as a safety valve back from raw text to the dialog whenever possible. [Recommend keeping it, same reasoning as spec 005's analogous open question 2: it is cheap and avoids ever trapping a sheet in a dead end.]
