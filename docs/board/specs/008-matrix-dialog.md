# 008 Dialog-based vector/matrix insertion

Source inspiration (concept only, nothing copied):
- https://en.wikipedia.org/wiki/Dialog_box (general, vendor-neutral description of the modal-dialog pattern; public, 2026-10-28). Same citation spec 006 already used: a form-style dialog with labelled fields and commit/cancel buttons is ordinary OS/toolkit chrome, the same chrome this app's existing Save/Save-As dialogs and spec 006's plot dialog already use. The "size picker, then a grid of cells" shape used below is the same kind of two-step dialog countless kinds of software use to create a table or grid of anything (a plain spin-box pair for rows/columns, then a plain editable grid widget); it is not a technique tied to engineering-calculation tools.
- https://docs.sympy.org/latest/modules/matrices/matrices.html (BSD-licensed library docs), already cited by spec 002, re-cited here only to confirm the matrix-literal shape this dialog targets is the one 002a already implemented. No new vendor source consulted for this spec.
- No Mathcad, Mathematica, Maple or other vendor software, documentation or screenshot was read or consulted for this spec. No vendor dialog's field order, labels, icons, button wording or workflow is described or used anywhere below. Field grouping, the size-picker/grid-of-cells split, the add/remove-row/column design, the Name/Show/Scale-unit fields and the "Edit as grid..." entry point are this spec's own design choices.
- Note for the manager: this spec reuses spec 006's already-approved pattern (a generic labelled-field/grid modal dialog compiling to and from existing text syntax, with a raw-text fallback) per the precedent recorded in docs/board/log.md and the IP check below, but it is **not** a drop-in copy of spec 006's trigger design. Spec 006's `PlotRegion` is a dedicated region type whose entire stored text *is* the plot spec, so double-click could safely open the dialog in place of the region's own raw multi-line editor. A math region (`livesheet/gui/regions.py::MathRegion`) instead holds one free-text statement that may or may not contain a matrix literal at all (`x := 5 m`, `A + [1, 2, 3; 4, 5, 6]`, plain text, etc.), and double-click's single existing meaning (start inline editing) is shared by every math region in the app, not just ones that happen to hold a matrix. This spec therefore keeps double-click's meaning unchanged everywhere and adds a separate, narrower entry point (see Trigger below and Open question 1) rather than overriding double-click's meaning for a subset of math regions.
- Note on numbering: this spec was originally drafted as 007, but spec number 007 was taken in parallel by the gui-specialist's `docs/board/specs/007-main-window.md`; this file was renumbered 008 before handoff (the stale `docs/board/specs/007-matrix-dialog.md` file has been replaced with a pointer to this one).

Interop: this is a GUI-only presentation layer on top of spec 002a. It does not change `livesheet/engine/matrices.py`, `livesheet/engine/evaluator.py`'s matrix pre-parse step, or `livesheet/engine/syntax.py`. It does not change `livesheet/document.py`: a `MathRegion` already stores nothing but `text` (no `w`/`h`, no `FORMAT_VERSION` bump needed, unlike spec 006's plot-region size fields). A matrix/vector inserted or edited through this dialog compiles to exactly the same `[a, b; c, d]`-style text spec 002a already parses, so every acceptance criterion of spec 002a keeps holding unchanged; this spec only adds criteria for the new entry points into creating/editing that text.

Size: two phases, about 2.5-3 days total (smaller than spec 006: no live-apply/preview is needed for a static grid of values, and there is no separate raw multi-line editor to build — the existing single-line inline editor is reused unchanged as the raw-text fallback).
- **Phase M1 (size picker, grid-of-cells step, compile, new-insertion OK/Cancel)**: the two-step dialog (rows x cols spin boxes, then the editable grid with Add/Remove row/column), the Name mode switch, the Scale/unit field, the Show-result mode switch, compiling to 002a's text format, wiring `Insert > Matrix` / a "Matrix here" canvas entry to create a brand-new math region from the compiled text via the existing `Worksheet.insert_region("math", initial_text=...)` path. About 1.5 days.
- **Phase M2 (decompose existing text, "Edit as grid..." context-menu entry, "Edit as text" escape hatch, cell/name/unit error checks)**: `decompose_matrix_text`, the "representable" rule, the context-menu entry added to `Worksheet.contextMenuEvent` for a right-clicked, representable, not-currently-editing math region, the dialog's own pre-compile checks (blank cells, embedded separators, blank name), and OK/Cancel on an existing region. About 1-1.5 days.

---

## User story
As an engineer placing a stiffness matrix or a load vector, I open a small dialog instead of typing brackets, commas and semicolons by hand: I pick how many rows and columns I need, fill in one text box per cell, optionally give it a name and a unit, and confirm. I get back exactly the same `[1, 2; 3, 4]`-style text the worksheet already understands, so nothing about how matrices are stored, computed or displayed changes — only how I type one in.

## Behaviour (own words)

### Trigger
- `Insert > Matrix` (new entry next to the existing `Insert > Math Region`/`Text Region`/`Plot`) and a new "Matrix here" entry in the canvas's right-click context menu (next to the existing "Plot here", shown only when the right-click did not land on an existing region) both open the dialog's Size step at the clicked/crosshair position. Nothing is created on the canvas yet (unlike spec 006's plot dialog, where the region exists while the dialog is open; here, because there is no live chart to preview, the dialog can stay entirely off-canvas until OK).
- Right-clicking an **existing** math region that is not currently being edited, and whose current `source` text is "representable" (see Advanced/raw-text fallback below), shows a new "Edit as grid..." entry in its context menu; choosing it skips the Size step and opens the Grid step directly, pre-filled by decomposing the region's current text. A region whose text is not representable, or that is currently being edited, shows no such entry; right-click on it (or anywhere else) behaves exactly as it does today.
- Double-clicking any math region keeps today's unchanged meaning: it starts inline text editing in place, whether or not the region holds a matrix literal (see the note above and Open question 1).
- The dialog is modal, with a title bar and Next/Back (between the two steps) and OK/Cancel/"Edit as text" buttons — the same plain dialog chrome spec 006 already uses.

### Size step
- Two spin boxes, "Rows" and "Columns", each 1-20 (this dialog's own usability cap, well under 002a's 200-size hard limit and separate from its 10x10 display-placeholder threshold; see Open question 4). Default 2x2 for a brand-new insertion.
- "Next" opens the Grid step sized accordingly, with every cell blank. "Cancel" here creates nothing at all.
- Going back from the Grid step to the Size step and changing rows/columns keeps already-typed cells that still fit the new shape (same row, same column index) and blanks any newly added cells; shrinking drops cells that no longer fit. This is this spec's own choice, not drawn from any vendor behaviour.

### Grid step
- **Elements**: a rows x columns grid of single-line text boxes, one per cell, filled left to right, top to bottom. Each box holds the exact element text that will appear between the matching comma/semicolon in the compiled literal — a plain number, a signed number, a fraction (`1/3`), a bare name, or a short expression (`a+1`, `sin(0.5)`), exactly as 002a already allows inside `[...]`. "Add row"/"Remove row" and "Add column"/"Remove column" buttons grow or shrink the grid by one at a time (disabled at the 1 and 20 bounds), the same generic add/remove pattern spec 006 already uses for its Function(s) list, extended to two dimensions.
- **Name**: a mode switch, default "No name (insert as a value)". The other mode, "Define as", shows a name text box plus a choice of assignment kind, "`:=` Definition" or "`≡` Global definition" (the same two wordings already used by the existing `Insert` menu's token entries in `main_window.py`, reused here for consistency, not vendor-derived).
- **Scale/unit**: one optional text box, labelled "Scale/unit factor", appended after the bracket literal as `*FACTOR` (matching 002a's own stiffness-matrix example `[2, -1; -1, 2]*N/m`). Blank means no suffix. Named "Scale/unit" rather than just "Unit" because the field is really a trailing multiplicative factor (it could just as well be a plain number or another defined name), matching what 002a's grammar actually allows there.
- **Show result**: a mode switch, default "Don't show a result". The other two modes are "Show numeric result (`=`)", with an optional "display unit" text box next to it, and "Show symbolic result (`→`)". These map to 002a's own `=`/`→` suffixes; the "display unit" box maps to the optional unit text after `=` (`F = kN`), matching 002a's own target-unit convention.

### Compiling to the existing text format
The dialog state compiles, in this fixed order, to exactly the text 002a already parses: `[` then the grid's rows, each row's cells joined by `, `, rows joined by `; `, then `]`; then `*FACTOR` if the Scale/unit box is filled; the whole thing prefixed by `NAME := ` or `NAME ≡ ` if "Define as" was chosen; and suffixed by ` =` (plus ` UNIT` if the display-unit box is filled) or ` →` if a Show-result mode other than "Don't show" was chosen. This is exactly 002a's own bracket-literal grammar (no new engine syntax) and is what gets written into `RegionData.text`/`MathRegion.source`.

### New insertion: OK / Cancel
- **OK** on the Grid step, for a brand-new insertion (reached via `Insert > Matrix`/"Matrix here"), creates a new math region via the existing `Worksheet.insert_region("math", initial_text=compiled_text)` path — the same mechanism the Math toolbar's token buttons (`sqrt(`, `diff(`, …) already use — and leaves the region in its normal inline-edit state with the cursor at the end of the inserted text, exactly as those toolbar buttons do today. The user can keep typing (e.g. append more to the expression) or click elsewhere to commit, triggering the normal `Engine.evaluate` pass unchanged.
- **Cancel** at either step, for a brand-new insertion, creates nothing: the canvas is left exactly as it was before `Insert > Matrix`/"Matrix here" was chosen. This is simpler than spec 006's Cancel rule because, unlike a plot dialog that needs a live region on-canvas for Apply to update a chart, nothing needs to exist on the canvas before OK here.

### Editing an existing region: OK / Cancel
- **OK** on the Grid step, reached via "Edit as grid..." on an existing representable region, writes the compiled text into that region's `source`/`RegionData.text` and closes the dialog; the normal `Engine.evaluate` pass runs exactly as it would after any ordinary text edit (no new evaluation entry point).
- **Cancel** reverts nothing (the region's `source` was never touched while the dialog was open) and simply closes the dialog, leaving the region exactly as it was before "Edit as grid..." was chosen.

### Error handling
- Checked by the dialog itself before compiling (own messages, no engine call): every cell must be filled ("Every cell must have a value", shown at that cell); a cell's text must not contain a top-level comma or semicolon ("A cell cannot contain ',' or ';'; use Add column/Add row instead" — reusing the same bracket-aware top-level scan 002a's own pre-parse step already needs, so a cell like `f(a, b)` is fine but `1, 2` in one box is rejected); when "Define as" is chosen, the name must be non-blank ("Name is required").
- Anything else is only known once the compiled text is actually committed and evaluated, exactly as for any direct text edit today: a malformed cell expression, a name already used, "`<name>` is not defined" for a symbolic cell shown with `=`, "Units do not match" for a mismatched display unit on a mixed matrix, or a nested-bracket cell triggering 002a's existing "Nested matrices are not supported" error. Because OK always closes this dialog (there is no Apply/live-preview button, unlike spec 006 — see Open question 3), such an error surfaces on the committed region itself, the same way it would if the same text had been typed directly and then committed.

### Advanced/raw-text fallback
A math region's current `source` is "representable" by this dialog exactly when, after stripping an optional leading `NAME :=` or `NAME ≡` assignment, it is exactly one bracket literal of 002a's matrix/vector grammar, optionally followed by a single `*FACTOR` term with no top-level `+`/`-` (reusing 002a's own bracket-aware splitting, not a new parser), optionally followed by a trailing ` =` (with or without a unit) or ` →`, and nothing else. Any other content — two bracket literals, a matrix combined with `+`/`-`, a matrix passed to a function, keyword chains after `→`, or anything not matching this shape — is not representable: no "Edit as grid..." entry appears for it, and both double-click and any other editing path are completely unchanged from today.
The Grid step also offers an **"Edit as text"** button (next to Cancel) that discards any in-dialog changes and calls the region's own existing `start_editing()` (today's inline editor) — for a brand-new insertion this simply closes the dialog without creating anything (same as Cancel). There is no reciprocal "Use dialog..." button inside the compact inline editor itself (see Open question 2); the only way back into the dialog for an existing region is the "Edit as grid..." context-menu entry once editing has finished.

### Resize, move, delete, save/reload — unchanged
A region created or edited through this dialog is an ordinary `MathRegion`; nothing about `RegionData`, `FORMAT_VERSION`, resize handles, moving, selecting, or single-owner deletion changes. Which entry point a region can be opened through next ("Edit as grid..." available or not) is re-derived from its stored text every time, exactly as spec 006 already does for plots; it is not itself a saved property.

## Syntax proposal (own keywords)
No new engine syntax. The compiled text uses only 002a's existing bracket-literal grammar (`[a, b; c, d]`), its `:=`/`≡` assignment operators, and its `=`/`→` display suffixes, in the fixed order given under "Compiling to the existing text format". No change to `livesheet/engine/syntax.py` or `livesheet/engine/matrices.py`.

## Acceptance criteria
GUI-level; references to "criterion N of spec 002a" mean `docs/board/specs/002-vectors-matrices.md`'s 002a acceptance criteria.

Trigger and pre-fill
1. `Insert > Matrix` (or "Matrix here") opens the Size step with Rows=2, Columns=2 pre-filled. Clicking Cancel on the Size step leaves no region on the canvas.
2. From the Size step, setting Rows=3, Columns=1 and clicking "Next" opens the Grid step with a 3x1 grid of blank cells, Name "No name", Show "Don't show a result", Scale/unit blank.
3. Right-clicking an existing math region whose text is `A := [1, 2; 3, 4]` (002a criterion 1's definition, no trailing `=`) shows "Edit as grid..."; choosing it opens the Grid step pre-filled: Name "Define as" `A` (`:=`), a 2x2 grid with cells `1`, `2`, `3`, `4` (row-major), Scale/unit blank, Show "Don't show a result".
4. Right-clicking a math region whose text is `A := [1, 2; 3, 4] =` (002a criterion 1 exactly, with its trailing display) pre-fills the same as 3 plus Show "Show numeric result (=)" with the display-unit box blank.
5. Right-clicking a math region whose text is `K := [2, -1; -1, 2]*N/m` (002a's own stiffness-matrix example) pre-fills Name `K`, a 2x2 grid with cells `2`, `-1`, `-1`, `2`, Scale/unit `N/m`, Show "Don't show a result".
6. Right-clicking a math region whose text is `A + [1, 2, 3; 4, 5, 6]` (002a's own size-mismatch example, two terms) shows no "Edit as grid..." entry at all; double-clicking it still starts today's ordinary inline text editing, unchanged.
7. Right-clicking a math region whose text is `M := [a, b; c, d]` (002a's symbolic example) pre-fills grid cells `a`, `b`, `c`, `d` as plain text.

Fields and compile mapping
8. Size step 2x2, Grid step cells `1`, `2`, `3`, `4` (row-major), Name "No name", Show "Don't show a result", Scale/unit blank: OK inserts a new math region with text `[1, 2; 3, 4]`, left in inline-edit state with the cursor at the end; clicking elsewhere to commit reproduces 002a criterion 1's result once the region is also given the name/display it needs (this criterion checks the inserted text only, criterion 9 checks the full round trip).
9. Same grid, Name "Define as" `A` (`:=`), Show "Show numeric result (=)" with the display-unit box blank: OK inserts `A := [1, 2; 3, 4] =`; after committing, `region.result.output` is identical to 002a criterion 1's.
10. Same grid, Scale/unit `N/m`, Name "Define as" `K` (`:=`): OK inserts `K := [2, -1; -1, 2]*N/m`, matching 002a's own example text exactly, byte for byte.
11. On a 2x2 grid, "Add column" adds one blank cell to each existing row (now 2x3); "Remove row" removes the last row and its cells. The compiled text always reflects the grid's current shape (row-major, `, ` between elements, `; ` between rows), matching 002a's own literal syntax.
12. Rows=1, Columns=3, cells `5`, `6`, `7` compiles to `[5, 6, 7]` (002a criterion 2's row-vector case); Rows=3, Columns=1, cells `5`, `6`, `7` compiles to `[5; 6; 7]` (criterion 2's column-vector case).
13. Rows=1, Columns=1, cell `5` compiles to `[5]` (002a's 1x1-literal edge case).

OK / Cancel, new insertion
14. Clicking Cancel on either the Size step or the Grid step during a brand-new `Insert > Matrix`/"Matrix here" leaves the canvas exactly as before: no region is ever created.
15. Clicking OK on a brand-new insertion has exactly the same net effect as typing the compiled text directly into a freshly inserted math region (`Insert > Math Region`) and committing it: identical `region.result` for identical text.

OK / Cancel, existing region
16. Choosing "Edit as grid..." on an existing region (criterion 3's region), changing a cell, then clicking Cancel: `region.source`/`RegionData.text` is left exactly as it was before "Edit as grid..." was chosen; nothing from the dialog session is written.
17. Choosing "Edit as grid..." on criterion 4's region, changing cell `4` to `40`, then clicking OK: the region's text becomes `A := [1, 2; 3, 40] =` and `region.result.output` updates accordingly, the same as if `40` had been typed directly in place of `4` using today's inline editor.

Errors
18. Leaving any cell blank and clicking OK: the dialog's own message "Every cell must have a value" is shown at that cell; OK is refused, nothing is created or changed.
19. Typing `1, 2` into a single cell and clicking OK: the dialog's own message "A cell cannot contain ',' or ';'; use Add column/Add row instead" is shown at that cell.
20. "Define as" with the name box left blank and clicking OK: the dialog's own message "Name is required" is shown at the Name field.
21. Grid cell `Y` (undefined) with Show "Show numeric result (=)", on an otherwise-empty sheet: OK commits and closes the dialog; the region then shows 002a criterion 24's `Y is not defined` error family, exactly as it would if `[Y] =` had been typed directly.

Raw-text fallback
22. "Edit as text" on the Grid step, for an existing region, discards any in-dialog changes, closes the dialog and calls the region's existing `start_editing()`; the region's text is unchanged from before the dialog opened. For a brand-new insertion, "Edit as text" behaves exactly like Cancel (nothing is created).
23. There is no "Use dialog..." control inside the plain inline editor; the only way to reach the Grid step for an existing region is "Edit as grid..." from its context menu once it is not being edited (see Open question 2).

Regression
24. Save and reload round-trip exactly as today: `RegionData`/`FORMAT_VERSION` are unchanged; a region created via this dialog is byte-for-byte indistinguishable on disk from the same text typed directly.
25. Resize is not applicable (math regions auto-size to content, unchanged); moving, selecting, and single-owner deletion behave exactly as any other `MathRegion` today.

## Edge cases
- The dialog's own 1-20 grid-size cap is separate from 002a's 200-size hard limit and its 10x10 display-placeholder threshold (criterion 5 of 002a); a matrix bigger than 20x20 continues to be typed directly, unchanged.
- Cells carry no syntax checking beyond "non-blank" and "no top-level `,`/`;`"; a malformed expression (`1+`) is only caught once OK commits the text, exactly as a direct edit would catch it today.
- A cell containing its own bracket literal is not specially checked by the dialog; it surfaces 002a's existing "Nested matrices are not supported" error once committed.
- Going back from the Grid step to the Size step keeps cells that still fit the new shape and blanks the rest (own design choice, stated under Behaviour above).
- A region whose text has the matrix literal combined with any other operator (`A := [1,2] + [3,4]`, `det([1,2;3,4])`, `f([1,2;3,4])`) is never representable; "Edit as grid..." never appears for it, and raw text editing is the only path, unchanged from today.
- This dialog never checks whether a "Define as" name collides with one already defined elsewhere on the sheet; that is left to the existing engine rule (evaluation order top to bottom, redefinition/`not defined` errors), unchanged.

## IP check
Pass. This design reuses spec 006's already-approved reasoning: a modal dialog with plain spin boxes (rows/columns), an editable grid of text cells with add/remove row/column buttons, and OK/Cancel/"Edit as text" buttons is one of the most generic UI patterns in all of software — the same shape used by, among many others, any "insert table" size-picker or spreadsheet cell-range editor across office and spreadsheet software generally, not a technique specific to, or associated with, engineering-calculation tools. Nothing is drawn on or interleaved with the worksheet canvas at any point; the dialog is a separate top-level widget, and (unlike spec 006's Apply button) there isn't even a live-preview concern here, since a matrix dialog has no chart to update live — OK always simply writes finished text once, the least "live" of the two designs. The matrix bracket-literal syntax itself (`[1, 2; 3, 4]`) is already-approved generic notation from spec 002a's own IP check, unchanged here. No vendor dialog's field order, labels, icons, button wording or workflow was read, described or used; the size-picker/grid-of-cells split, the Name/Scale-unit/Show-result fields, the add/remove-row/column design and the "Edit as grid..." context-menu entry point are this spec's own choices. No known patent concern for a standard size-picker-plus-grid configuration dialog; not legal advice.

## Fits current architecture?
- `livesheet/engine/matrices.py`, `livesheet/engine/evaluator.py`, `livesheet/engine/syntax.py`: unchanged.
- `livesheet/document.py`: unchanged (no new `RegionData` field, no `FORMAT_VERSION` change).
- New `livesheet/gui/matrixdialog.py`: `MatrixDialog` widget (Size step, Grid step, Name mode switch, Scale/unit field, Show-result mode switch, OK/Cancel/"Edit as text"/Next/Back), plus two Qt-free helper functions `compile_matrix_fields(...) -> str` (fields to 002a text, the Compiling section's fixed order) and `decompose_matrix_text(text) -> fields | None` (the inverse, `None` for non-representable text), named to match spec 006's `compile_plot_fields`/`decompose_plot_text` convention and reusing the bracket-aware element-splitting already needed by 002a's own `[...]` pre-parse step rather than writing a new parser.
- `livesheet/gui/worksheet.py`: new `insert_matrix_at(pos)` mirroring the existing `insert_plot_at(pos)`, but using the already-existing `insert_region("math", initial_text=compiled_text)` path (today used by the Math toolbar's token buttons) rather than a new region-creation branch; `contextMenuEvent` gains a "Matrix here" entry (blank canvas, alongside "Plot here") and an "Edit as grid..." entry when the right-click lands on a non-editing `MathRegion` whose `source` passes `decompose_matrix_text`.
- `livesheet/gui/main_window.py`: new `&Matrix…` entry in the `&Insert` menu, next to the existing Math/Text/Plot entries, wired to `insert_matrix_at`/the dialog.
- `livesheet/gui/regions.py`: unchanged (`MathRegion.start_editing()`/`finish_editing()` are reused as-is for "Edit as text" and for committing the dialog's compiled text).
- Tests: new `tests/test_matrix_dialog.py` for criteria 1-25 (Qt-free compile/decompose tests plus Qt dialog tests, Qt parts skip when PySide6 cannot load, same convention as `tests/test_plot_dialog_dev.py`); existing `tests/test_matrices.py`/`test_matrices_b.py` need no changes since the engine is untouched. The tester should also launch the real app and exercise: `Insert > Matrix` and "Matrix here" through Size/Grid/OK, Cancel at both steps, Add/Remove row/column, both Name modes, both Show modes, the cell/name validation messages, "Edit as grid..." on representable and non-representable regions (including right-click while another region is mid-edit), "Edit as text", and save/reload — on Theo's Mac, not only headless.
